Refresh_token phase:
In this phase the user already has an account and has logged in already but the access token we gave him got expired
he can contact /auth/refresh (name can change for some reasons but the funcationality will be same).

When the users hit refresh route they are already an user and have a valid login session so we have to find that session by their given session id and they must also provide their refresh token that should not have been (rotated) or expired.
As of now the Session id and Refresh token gets automatically attached by browser on the post request to /auth/refresh. 
After running the verification checks we provide them an diffrent refresh token and an new access token.


The diffrent tokens provided and their goal:

Access Token ( Not Attached to cookies | To be stored in memory by client using js ) :
Purpose - To authenticate if the user sending the request to the server is an valid user or not. The access token is created using JWT_SECRET and the users own ID feild coming from database.
Benifits - We can achieve an serverless authentication if we provide this token: Since the id is the actual AccessToken we can directly get the userid for necessary actions
The Dangers / Tradeoffs ( Nothing is ever truly Free ) - We treat anyone holding an valid access token as an actual verified user but if the access token or the jwt secret gets leaked there will be a lot of trouble and security issues like anyone can access the users account and do modifications on behalf of the actual users, to mitigate that these tokens must be shortlived

Where to get AccessToken? - Currently all the auth routes like /auth/login, /auth/register and /auth/refresh gives user an new Access token


Refresh Token ( Attached to Cookies with an HTTPOnly attribute to avoid abuse in case of XSS ):
Purpose - To identify the user and they have an session with us ( wether they are logged in ), since the access token are shortlived we need an long lived token that can be used to get a new access token in place of the expired one and that token is Refresh token
The Dangers / Tradeoffs - This token must never be leaked because if it does the actual user can be locked from getting the access token, while the attacker can keep getting tokens pretending to be an user forever if no action is ever taken because these tokens are one time use only each requst to get new access token consumes the refreshtoken and provides a new one.
The Double edge sword - IF the Refresh token gets leaked but at the same moment actual user tries /refesh that old one that got leaked is no more valid but if the attacker does the refresh first with the leaked token and when its valid then token the actual user is holding is now invalid.

Precauctions taken - Given how troublesome the case is if the token gets leaked i have to make it even less likely for it to leak
To avoid theft via XSS ( cross site scripting ) scenario i send the token on an HTTPOnly cookie making this token unreadable by any js wether its my own code or an malicious code running on my codebase pretending to be mine.
To avoid csrf (Client side request forgery) where an malicious site rides the actual request and with the valid tokens attached by users browser the server checks origin of request if it comes from my own frontend url then let the request pass if not we return an unauthorized access status code.

The issue - Since i dont have domain YET the following things are hosted at these platform
The Backend - Render
The Database - Neon
The Frontend - Vercel

Since the backend and frontend have diffrent domain url we cant use the samesite:strict attribute to the cookies being sent by browser which is why we are depending on origin check
But its not really that dependable since i have no experince on if the origin can be altered in some way.
To fix this specific case, i learnt by how others handle this case and what i got was they provide an non Http only cookie thats readable by js and require it to be attached to the request header for verification
but it also needed me sending that http only cookie to same domain which meant that the cookie got stored for the backends domain not the frontend which still is not what i wanted so i kept the csrf token but made it so that now we send the token back to frontend in response body so they can attach it back to us and we then verify if it was signed by us and if its the same one we sent earlier
since the attacker can only read the non Http cookies of their own browser because of same origin policy he will only get his own cookies not the users cookie he cant attach the correct one to header, But by this addition now i have to make sure no XSS attacks happen.



Csrf Token (Sent to user in response body so their js can read it and attach in header): 

How its made? - its a random hex string generated by server and signed with signature to identify it was created by this server
It is built by crypto.Hmac given the servers CSRF_SECRET and the formula sha256 to ensure it is completely non guessable
It is to be stored in localstorage and sent to server when requesting refresh route, as its stored in localstorage because on its own its not very harmfull because if it ever leaks we have request orgin checks
for more info visit src/controllers/util-functions.ts

Purpose - to avoid csrf issues mentioned above
Benifits / Tradeoffs - Makes the flow more secure when paired with origin check but breaks if Xss happens on site
Precauctions - No dangerously set html rendered on clientside, the inputs must always be validated before storing in database, any user input data rendered by client should be tratead as a string not an additional code that can run.

Where to get csrfToken? - it gets sent by server on valid register / login or refresh too but it returns the same one you used to access refresh route
